# GAS 初接入：AbilitySystemComponent 与 AttributeSet

战斗、属性、技能终归要落在 GAS（Gameplay Ability System）上，这一篇把它请进门：开启插件、给工程建 ASC 与 AttributeSet 的自有子类、挂进 BaseCharacter，并在 Possess 时机调用 `InitAbilityActorInfo` 完成初始化。本篇不写任何技能也不定义任何属性——两个类还是空壳，先把"线"接对，"电"以后再通。

![GAS 组成示意](img/Gameplay%20Ability%20System.png)

ASC 是 GAS 的中枢：技能（GameplayAbility）的执行、属性（AttributeSet）的持有、效果（GameplayEffect）的施加、标签（GameplayTag）的判定都绕着它转。外部系统不直接找技能或属性，而是先拿到 ASC 再问它要——所以接入的第一件事，就是让角色"被问到 ASC 时答得上来"。

## 一、开启插件与模块依赖

编辑器 Edit → Plugins → 搜索 "Gameplay Abilities" → 勾选 Enabled → 重启编辑器：

![开启 Gameplay Abilities 插件](img/开启Gameplay%20Abilities插件.png)

开关一勾，`.uproject` 里多出一段：

```json
// Warrior.uproject
{
  "Name": "GameplayAbilities",
  "Enabled": true
}
```

光开插件还不够，C++ 侧要在 `Build.cs` 里声明模块依赖才能 `#include` 它的头文件：

```csharp
// Warrior.Build.cs
PublicDependencyModuleNames.AddRange(new string[]
{
    "Core", "CoreUObject", "Engine",
    "InputCore", "EnhancedInput",
    "GameplayTags",
    "GameplayTasks", "GameplayAbilities"   // 新增
});
```

`.uproject` 的 `AdditionalDependencies` 里也补了 `"GameplayAbilities"`——它把这个模块追加进游戏模块的构建依赖，效果与 Build.cs 里那行声明同源；两处都写是双保险的惯例，删掉其中一处通常也能编过，但没必要省。

两个容易含糊的点：

- **插件开关（uproject）≠ 模块依赖（Build.cs）**：前者说"这个插件在工程里可用"，后者说"我的代码要链接它"。只开插件不加依赖，`#include "AbilitySystemComponent.h"` 直接编译错误；只加依赖不开插件，模块压根不在，同样编不过；
- **`GameplayTasks` 与 `GameplayAbilities` 成对出现**：能力系统底层依赖 GameplayTasks（技能里的异步任务靠它跑），显式写出省得依赖传导的脑力开销。

## 二、两个空壳子类

```cpp
UCLASS()
class WARRIOR_API UWarriorAbilitySystemComponent : public UAbilitySystemComponent
{
    GENERATED_BODY()
};

UCLASS()
class WARRIOR_API UWarriorAttributeSet : public UAttributeSet
{
    GENERATED_BODY()
};
```

现在它们一行逻辑都没有，为什么要多此一举地继承一层，而不直接用引擎类？和当初自定义 `WarriorInputComponent` 同一个思路：**引擎类是不许动的黑盒，自有子类是留给未来的挂点**。后面技能输入确认的拦截、属性变化的钳制（Clamp）逻辑，总得有个地方写——到时候写在自己类的 `.cpp` 里，而不是散在各处调用点。空壳先占位，占的就是这个"名分"。

## 三、BaseCharacter 集成

```cpp
// WarriorBaseCharacter.h
UCLASS()
class WARRIOR_API AWarriorBaseCharacter : public ACharacter, public IAbilitySystemInterface
{
public:
    virtual UAbilitySystemComponent* GetAbilitySystemComponent() const override;

protected:
    // ★ 每次被控制器接管时触发（对比 BeginPlay：一生只跑一次）
    virtual void PossessedBy(AController* NewController) override;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "AbilitySystem")
    UWarriorAbilitySystemComponent* WarriorAbilitySystemComponent;

    UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "AbilitySystem")
    UWarriorAttributeSet* WarriorAttributeSet;
};
```

```cpp
// WarriorBaseCharacter.cpp
AWarriorBaseCharacter::AWarriorBaseCharacter()
{
    WarriorAbilitySystemComponent = CreateDefaultSubobject<UWarriorAbilitySystemComponent>(TEXT("WarriorAbilitySystemComponent"));
    WarriorAttributeSet = CreateDefaultSubobject<UWarriorAttributeSet>(TEXT("WarriorAttributeSet"));
}

UAbilitySystemComponent* AWarriorBaseCharacter::GetAbilitySystemComponent() const
{
    return WarriorAbilitySystemComponent;
}

void AWarriorBaseCharacter::PossessedBy(AController* NewController)
{
    Super::PossessedBy(NewController);

    if (WarriorAbilitySystemComponent)
    {
        WarriorAbilitySystemComponent->InitAbilityActorInfo(this, this);
    }
}
```

四个动作各有各的用意：

- **继承 `IAbilitySystemInterface` 并实现 `GetAbilitySystemComponent`**——这是引擎约定的"标准问法"。任何外部系统（UI、AI、目标选取）拿到 Actor 后，通过接口统一索要 ASC，不必知道它内部哪个成员变量存着组件。不实现这个接口，通用获取函数（如 `GetAbilitySystemComponentFromActor`）会空手而归；
- **`CreateDefaultSubobject` 在构造函数里建组件**——组件随 CDO 模板默认构造，蓝图子类自动继承，蓝图里"看不见删不掉"，数据来源单一。`EditDefaultsOnly + BlueprintReadOnly` 的修饰策略延续前几篇的档位：实例不可换、运行时只读；
- **`PossessedBy` 里 `InitAbilityActorInfo(this, this)`**——**`PossessedBy`** 是本篇最核心的挂点，单独说；
- **写在 Base 而非 Hero**——敌人也有属性和技能，ASC 属于"所有可战斗角色"的公共设施，落点跟相机臂（Hero）、Debug 助手（全局）的分层判断一致。

## 四、InitAbilityActorInfo：Owner 与 Avatar

`InitAbilityActorInfo(OwnerActor, AvatarActor)` 告诉 ASC 两件事——**逻辑上归谁管，物理上附着在谁身上**：

- **OwnerActor**：ASC 的所有者，逻辑与网络权威方；
- **AvatarActor**：肉体，技能动画、碰撞、位置都体现在它身上。

单机英雄最简单的形态就是两个都填自己：`InitAbilityActorInfo(this, this)`。分离的形态在 GAS 项目里很常见——比如 Boss 的 ASC 由 AIController 或专门的"状态 Actor"持有（Owner），肉体 Pawn 只做 Avatar，网络模式下服务端权威也靠这个分离表达。现在填 `(this, this)`，将来哪个角色需要分离，只改它自己的初始化参数，接入框架不变。

时机选 `PossessedBy` 而不是 `BeginPlay`，关键不在先后而在**触发次数与约定位置**：

::: tip 两个生命周期函数的"档期"对比
- **`PossessedBy`**——每次被控制器接管时都触发：Pawn 被复用、换控制器，它跟着再来一遍，初始化不会失效；
- **`BeginPlay`**——一生只跑一次，重 Possess 时不会再叫醒它。
:::

**`PossessedBy`** 同时是 GAS 双端初始化约定的服务端半边：将来做多人时，客户端在 `OnRep_PlayerController` 里补另一半，同一个函数名各端各写，接入框架现在就位。

## 五、Hero 侧验证

```cpp
void AWarriorHeroCharacter::PossessedBy(AController* NewController)
{
    Super::PossessedBy(NewController);   // 链回 Base，里面完成了 InitAbilityActorInfo

    if (WarriorAbilitySystemComponent && WarriorAttributeSet)
    {
        const FString ASCText = FString::Printf(TEXT("Owner Actor: %s, AvatarActor: %s"),
            *WarriorAbilitySystemComponent->GetOwner()->GetActorLabel(),
            *WarriorAbilitySystemComponent->GetAvatarActor()->GetActorLabel());
        Debug::Print(TEXT("Ability system component valid.") + ASCText, FColor::Green);
        Debug::Print(TEXT("AttributeSet valid.") + ASCText, FColor::Green);
    }
}
```

PIE 跑起来，屏幕左上角两行绿字、Owner 与 Avatar 都是 `BP_HeroCharacter`，接入即告成立。两个细节：

- **`Super::PossessedBy` 必须先调**——Init 在 Base 的实现里，跳过 Super 就跳过初始化，后面的判空虽不炸但两条日志都不出。重写生命周期函数时 Super 调用是第一 reflex；
- **`GetActorLabel()` 是编辑器构建专属**（依赖 UnrealEd），PIE 里用着舒服，打包 Shipping 会编译不过。验证代码留在角色类里没关系，但要知道它出不了编辑器的门。

## 六、细节与坑

1. **只开插件不加 Build.cs 依赖**——`#include "AbilitySystemComponent.h"` 报"打不开文件"。插件开关管加载、模块依赖管链接，两步缺一不可；
2. **`.uproject` 与 `Build.cs` 改完不重启/不重编译**——插件启用必须重启编辑器；Build.cs 改动靠重新生成让 VS 拾取，直接编旧工程文件会链接到旧依赖表；
3. **忘了实现 `GetAbilitySystemComponent`**——编译直接报错（接口纯虚），这反而是好事；真正阴险的是返回错组件或返回 null，外部系统静默拿空；
4. **`InitAbilityActorInfo` 写进 `BeginPlay`**——**`BeginPlay`** 一生只执行一次，Pawn 被复用、换控制器接管时错过重新初始化；多人环境下客户端的 `OnRep_PlayerController` 半边也无处衔接。初始化跟着 Possess 走，不跟着播放走；
5. **`GetActorLabel` 打进 Shipping 包**——编辑器专属 API，打包编不过。调试打印要么留在开发配置，要么换 `GetName()`。

## 小结

- 接入三步：开插件（uproject）→ 加依赖（Build.cs，`GameplayTasks` 与 `GameplayAbilities` 成对）→ 建子类并挂进角色；插件开关管加载、模块依赖管链接，是一件事的两半；
- ASC 与 AttributeSet 各建一个空壳子类占位——引擎类是黑盒，自有子类是未来写输入拦截、属性钳制的挂点；
- BaseCharacter 多继承 `IAbilitySystemInterface` 统一"问 ASC"的入口；组件在 C++ 构造里 `CreateDefaultSubobject`，蓝图看得见换不得；
- **`PossessedBy`** 时机调 `InitAbilityActorInfo(this, this)`，Owner 与 Avatar 概念就此立住——单机先合一，将来 AI/网络角色的分离只改参数不改框架。
