# 面向对象特性与 Actor / Pawn / Character

写到这里，工程里已经同时存在 `MyActor`、`MyPawn`、`PlayerCharacter`、`SubPlayerCharacter` 四个自定义类——它们恰好是本章的现成素材：**UE 的类体系就是 C++ 面向对象特性的一次大规模实战**。本章先把继承、组合这些语言层面的东西讲清楚，再顺着 UE 的继承树看 Actor → Pawn → Character 这三个最重要游戏类的关系与选型。

---

## 一、面向对象三大特性 + 组合

### 1. 封装（Encapsulation）

把数据和操作数据的方法绑在一起，用访问权限控制外界能看到什么：

```cpp
UCLASS()
class MYTHIRD_API APlayerCharacter : public ACharacter
{
    GENERATED_BODY()

public:
    APlayerCharacter();

protected:
    // 子类和自己能访问，蓝图和外部类不能直接碰
    virtual void Attack();

private:
    // 只有本类自己能访问
    int32 InternalCounter;
};
```

C++ 的三档访问权限，在 UE 里配合 `UPROPERTY` 的 `BlueprintReadWrite / BlueprintReadOnly` 又叠了一层"对蓝图暴露多少"的控制——**访问权限是双轨的：C++ 一轨（public/protected/private），蓝图一轨（EditAnywhere/BlueprintReadOnly…）**。第 4 章的宏速查表里有完整对照。

### 2. 继承（Inheritance）

子类获得父类的全部属性和方法，并在其上扩展或修改。UE 里**一切游戏类都有共同的祖先 `UObject`**，它提供了垃圾回收、反射（UEditor 能看见你的属性就是靠它）、序列化这些底层能力——这些你一行代码都不用写，`UCLASS()` + `GENERATED_BODY()` 宏就继承下来了。

本工程的实例——`SubPlayerCharacter.h`：

```cpp
UCLASS()
class MYTHIRD_API ASubPlayerCharacter : public APlayerCharacter
{
    GENERATED_BODY()

public:
    virtual void Attack() override;
};
```

`ASubPlayerCharacter` 没写任何移动、相机、输入代码，但它**直接拥有** `APlayerCharacter` 的弹簧臂、相机、移动输入全套能力——这就是继承的复用价值。

### 3. 多态（Polymorphism）

同一个接口，不同实现。C++ 靠 **虚函数** 实现：父类声明 `virtual`，子类 `override`，调用时按**实际对象类型**决定执行谁的版本。

```cpp
// 父类 PlayerCharacter.cpp
void APlayerCharacter::Attack()
{
    UE_LOG(LogTemp, Log, TEXT("PlayerCharacter 普通攻击"));
}

// 子类 SubPlayerCharacter.cpp
void ASubPlayerCharacter::Attack()
{
    // 想复用父类逻辑就显式调用；想完全替换就不调
    Super::Attack();
    UE_LOG(LogTemp, Log, TEXT("SubPlayerCharacter 追加的攻击效果"));
}
```

多态的威力在"调用方不关心具体类型"：

```cpp
// 拿着一组角色，各自打各自的攻击——不需要 if/else 判断类型
TArray<APlayerCharacter*> Characters;
for (APlayerCharacter* C : Characters)
{
    C->Attack();  // ASubPlayerCharacter 实例执行的是重写后的版本
}
```

几个 UE 相关的注意点：

- `Super::Attack()` 是 UE 的宏写法，等价于 `APlayerCharacter::Attack()`，用于在子类里调父类版本（构造函数、`BeginPlay`、`Tick` 里都常见）；
- **UE 的虚函数几乎总是 `virtual … override` 成对出现**，忘了写 `override` 编译器不报错（除非开 `-Werror`），但拼错函数名时会静默变成一个新函数，坑很大；
- `UFUNCTION(BlueprintNativeEvent)` 是另一套"蓝图多态"机制：C++ 给默认实现、蓝图可覆盖，和纯 C++ 虚函数是互补关系。

### 4. 组合（Composition）

"有一个"而不是"是一个"：把功能拆成组件，按需拼装，而不是层层继承。UE 把这个思想做成了**组件模型**——这正是第 3 章讲过的内容，这里从设计角度再总结一次。

`ACharacter` 的移动能力不是它自己写的，而是持有一个 `UCharacterMovementComponent`：

```cpp
// 组合：Character "有一个" 移动组件
GetCharacterMovement()->MaxWalkSpeed = 500.f;

// 继承做不到的事：运行时换掉移动模式（行走 / 飞行 / 游泳）
GetCharacterMovement()->SetMovementMode(MOVE_Falling);
```

**继承 vs 组合怎么选**——经典口诀"组合优于继承"，在 UE 语境下对应关系是：

| | 继承（is-a） | 组合（has-a） |
|---|---|---|
| UE 形态 | `class ASubPlayerCharacter : public APlayerCharacter` | `CreateDefaultSubobject<USpringArmComponent>(…)` |
| 适合 | 强属关系、框架骨架（角色、游戏模式） | 可插拔功能（相机、移动、血量、背包） |
| 代价 | 继承链深了改一处动全身（脆弱基类问题） | 需要组件间通信（委托 / 接口，见第 3 章） |
| 本工程例子 | `SubPlayerCharacter` 复用整套角色能力 | `PlayerCharacter` 挂弹簧臂 + 相机 |

经验法则：**想给"一类东西"加能力 → 继承；想给"一个东西"加功能 → 组件**。角色要跳跃就继承 Character（框架能力），要背包就写个 `UBagComponent` 挂上去（可选功能）。

## 二、Actor / Pawn / Character 继承链

### 1. 继承树总览

```
UObject                    ← 反射 / GC / 序列化的根
  └─ AActor                ← 能放进关卡的一切
       └─ APawn            ← + 能被 Controller 控制的 Actor
            └─ ACharacter  ← + 胶囊碰撞 + CharacterMovement（行走/跳跃/动画驱动）
```

每一层只回答一个问题：

| 类 | 回答的问题 | 关键新增 |
|---|---|---|
| `AActor` | "**能放进世界里吗？**" | Transform（位置/旋转/缩放）、Tick、组件挂载、生成/销毁（SpawnActor / Destroy）、复制（网络） |
| `APawn` | "**能被操纵吗？**" | 被 `AController`（PlayerController / AIController） Possess；`SetupPlayerInputComponent` 接收输入 |
| `ACharacter` | "**能像'人'一样动吗？**" | 胶囊体碰撞、`UCharacterMovementComponent`（行走/奔跑/跳跃/坠落/游泳）、网格体挂点、根运动动画支持 |

### 2. AActor：世界里一切物体的基类

最普通的"东西"：摆锤、检查点、触发器、灯光——不需要被控制，也不需要人形的移动逻辑。本工程的 `MyActor` 就是裸骨架：

```cpp
UCLASS()
class MYTHIRD_API AMyActor : public AActor
{
    GENERATED_BODY()

public:
    AMyActor();

protected:
    virtual void BeginPlay() override;

public:
    virtual void Tick(float DeltaTime) override;
};
```

蓝图第 5 章做的大摆锤、滚木，用 C++ 实现的话就该继承 `AActor`（旋转逻辑写在 `Tick` 或用 Timeline）。**Tick 默认开启，不需要每帧逻辑时建议关掉省性能**：

```cpp
AMyActor::AMyActor()
{
    PrimaryActorTick.bCanEverTick = false;  // 不需要每帧逻辑就关掉，省性能
}
```

### 3. APawn：可被控制的 Actor

Pawn 在 Actor 之上加的核心概念是 **"被 Controller 占有（Possess）"**：

```
PlayerController ──Possess──▶ APawn
        │                          │
        └───── 输入（IA/IMC）──────┘
```

- `APlayerController` 把键盘/鼠标输入通过 `SetupPlayerInputComponent` 喂给 Pawn——所以**自定义 Pawn 必须重写这个函数**才能响应输入（本工程 `MyPawn.h` 里有这个空骨架）；
- `AAIController` 也能占有 Pawn，AI 路径同样走这里——**Pawn 是"玩家和 AI 共用的可控制体"**，这是它比 Character 更通用的地方；
- Pawn **不默认带碰撞和移动能力**：想移动要么自己写 `Tick` 改位置，要么挂 `UFloatingPawnMovement` 之类的组件。

典型用法：载具、飞行器、俯视角飞船、 spectator 观战相机——"可控但不是人形角色"的东西。

### 4. ACharacter：人形移动的完整方案

Character 在 Pawn 之上把"人怎么动"整个预置好了：

- **胶囊体**（`GetCapsuleComponent()`）：碰撞外形，RootComponent；
- **骨骼网格体挂点**（`GetMesh()`）：接动画蓝图、播放根运动；
- **`UCharacterMovementComponent`**：走路、跳跃、下落、游泳、爬楼梯、网络同步一整套——`MaxWalkSpeed`、`JumpZVelocity`、`bOrientRotationToMovement` 这些第 1、5 章调的参数全在这里。

代价是"重"：不需要人形移动的东西用 Character 是浪费。本工程的 `PlayerCharacter` 继承它，因为它就是第三人称人形角色——第 1 章开头那些 `GetCharacterMovement()->…` 配置，全是在给这套预置能力调参。

### 5. 选型速查

| 需求 | 用什么 | 本工程对应 |
|---|---|---|
| 场景机关、触发器、道具、灯光 | `AActor` | `MyActor`（练习）；蓝图版的摆锤/检查点 |
| 可被玩家/AI 控制但非人形（车、船、飞行器） | `APawn` | `MyPawn`（练习） |
| 人形角色（走路/跳跃/动画） | `ACharacter` | `PlayerCharacter` |
| 在角色基础上变体（新职业、新怪） | 继承现有 Character | `SubPlayerCharacter` |

一个容易混淆的点：**GameMode 不是这条链上的一环**。`AGameModeBase` 直接继承 `AActor`（且只存在于服务器），它负责"规则"（默认 Pawn 是谁、怎么重生），不负责"被控制"——见第 1 章。

## 三、把两条线合起来：UE 的设计哲学

回头看会发现 UE 的类体系是继承和组合的分工协作：

- **继承链（Actor → Pawn → Character）解决"身份"问题**：你是什么，决定了框架怎么对待你（能不能进关卡、能不能被控制、怎么移动）；
- **组件系统（组合）解决"能力"问题**：你有什么，全靠挂组件拼装（相机、弹簧臂、移动、血量、音效）。

`ACharacter` 自己就是最好的例子：它**继承** Pawn 拿到"可被控制"的身份，再**组合** `UCharacterMovementComponent` 拿到移动能力。理解了这个双轨结构，之后再遇到任何 UE 类，先问两个问题：*它在继承树的哪一层（身份）？它默认挂了哪些组件（能力）？*——比死记 API 有效得多。

---

## 小结

- 封装 / 继承 / 多态是 C++ 语言层特性，UE 用 `UPROPERTY` 等宏在蓝图方向又包了一层；
- 组合（组件）与继承（类链）配合使用：身份用继承，能力用组件；
- `AActor` = 能放进世界，`APawn` = 能被控制，`ACharacter` = 人形移动方案，逐层做加法；
- `Super::` 调父类、`virtual/override` 成对写、不需要 Tick 就关掉；
- 本工程对应文件：`MyActor` / `MyPawn`（骨架练习）、`PlayerCharacter`（Character 完整用法）、`SubPlayerCharacter`（继承 + 多态练习）。
